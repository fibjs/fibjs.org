# Finding the Performance Killer

Performance optimization of online services is often seen as an almost superstitious pursuit. A group of programmers stares at piles of obscure code, each guessing whether it is someone else who is exhausting the CPU. To find the performance bottleneck, they spend a great deal of time writing logs and poring over huge volumes of logs day and night. With fibjs, however, all of this becomes simple, because fibjs provides powerful CPU and memory profiler support that is very convenient to use.

In modern software development, performance optimization is an essential part that cannot be ignored. Whether it is a small application or a large distributed system, performance problems directly affect user experience and system stability. Traditional performance optimization methods usually rely on developers' experience and intuition, which is not only time-consuming and labor-intensive but also often fails to find the real performance bottleneck. To optimize performance more efficiently, we need professional tools to perform precise performance analysis.

fibjs is a high-performance JavaScript engine designed specifically for server-side applications. It not only provides a rich set of function libraries but also has built-in powerful performance analysis tools. By using fibjs's CPU and memory profiler, we can easily capture application performance data and generate detailed analysis reports. These reports are presented as flame graphs, which intuitively show the CPU usage of each function in the application, helping us quickly locate performance bottlenecks.

## Recording Logs

Starting fibjs's CPU profiler is extremely simple: just add the `--prof` option at startup. The default log recording interval is 1000ms, but as your optimization work goes deeper, you may need higher-precision analysis logs; in that case, you can use the `--prof-interval` option to set the interval. The following example shows how to record a fibjs work log every 10ms:

```sh
fibjs --prof --prof-interval=10 main.js
```

### Log Recording Interval

The log recording interval is the time interval at which the profiler records CPU usage. By default, fibjs records a log every 1000ms, which is sufficient for most applications. In some cases, however, you may need higher precision to capture short-lived performance fluctuations. By setting the `--prof-interval` option, you can adjust the log recording frequency. For example, setting it to 10ms captures CPU usage in finer detail but also generates more log data.

## Processing Logs

After the program exits normally or you terminate the process with `Ctrl+C`, a log file is generated in the current directory, with a name like `fibjs-xxxx.log`. You can then use the `--prof-process` option to process the generated log:

```sh
fibjs --prof-process fibjs-xxxx.log prof.svg
```

Once processing is complete, you can open the `prof.svg` file in a browser to view the flame graph for this log:

![prof](./imgs/prof.svg)

You can click to view the full-size image. In the full-size image, you can use the mouse to inspect more detailed information: [prof.svg](./imgs/prof.svg).

### Log File Naming

The generated log file name usually contains a timestamp or another unique identifier to ensure that the log file generated by each run is not overwritten. This allows you to run the profiler at different points in time and compare performance data from different time periods.

## Reading the Flame Graph

The flame graph is a powerful tool for analyzing and optimizing performance. Through the flame graph, you can intuitively see which parts of the application consume the most CPU time, helping you find performance bottlenecks and optimize them.

### Meaning of the Color Blocks

Each color block in the flame graph represents one recording point; the longer the block, the more times that function was recorded during the sampling period. Each row represents one level of the call stack; more rows mean deeper call nesting. The call stack is laid out upside down: the blocks closer to the bottom are the earlier functions.

### Colors of the Blocks

In fibjs's profiler, block colors fall into two categories:
- **Red**: represents JavaScript computation, usually CPU-intensive operations.
- **Blue**: represents IO operations or native computation, usually operations waiting for external resources, such as file reads and writes, database operations, and network operations.

### What to Focus On

Depending on the problem you need to solve, the area you should focus on differs:
- **Excessive CPU usage**: focus on the red blocks, which represent JavaScript computation, usually CPU-intensive operations.
- **Slow response times**: focus on the blue blocks, which represent IO operations or native computation, usually operations waiting for external resources.

### Length of the Blocks

The length of a block represents how many times that function was recorded during the sampling period. The longer the block, the more CPU time the function consumes. By observing the length of the blocks, you can intuitively determine which functions are performance bottlenecks.

### The Call Stack

Each level of the flame graph represents one frame of the function call stack: the bottommost level is the initial function call, and the higher you go, the deeper the call. By analyzing the flame graph, you can intuitively see which function calls consume the most CPU time.

### Areas of Focus

The larger blocks near the top are usually the parts that need the most attention and optimization. These blocks represent functions that consume a large amount of CPU time during the sampling period. By optimizing these functions, you can significantly improve the application's performance.

### A Practical Case Study

Suppose you have an online service, and users report that it responds more slowly during peak hours. You suspect that certain code sections are causing a performance bottleneck, so you decide to analyze it with fibjs's profiler.

First, start the service with the profiler enabled:

```sh
fibjs --prof --prof-interval=10 server.js
```

After running for a while during peak hours, terminate the process with `Ctrl+C` to generate the log file `fibjs-xxxx.log`. Then process the log file to generate the flame graph:

```sh
fibjs --prof-process fibjs-xxxx.log prof.svg
```

Open the `prof.svg` file and inspect the flame graph. You find a large patch of red blocks concentrated on a single function call, indicating that this function consumes a large amount of CPU resources. On further analysis of the code, you find an inefficient algorithm in that function. After optimizing the algorithm, you redeploy the service and test again with the profiler, and find that the red blocks in the flame graph are noticeably reduced and the service response speed is significantly improved.

In this way, you can easily find performance bottlenecks and optimize them in a targeted manner. Whether it is excessive CPU usage or slow response speed, the profiler can help you quickly locate the problem and thus improve the performance of your online service.

## Conclusion

By using fibjs's profiler, you can easily find performance bottlenecks and optimize them in a targeted manner. Whether it is excessive CPU usage or slow response speed, the profiler can help you quickly locate the problem and thus improve the performance of your online service.

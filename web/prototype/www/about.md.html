What is fibjs?

fibjs is an application server development framework designed mainly for web back-end development. It is built on top of Google's V8 JavaScript engine and adopts a concurrency approach different from traditional callbacks. fibjs uses fibers to isolate the business complexity introduced by asynchronous calls at the framework level, greatly reducing development difficulty and reducing the performance problems caused by frequent asynchronous processing in user space.

For historical reasons, JavaScript has mainly been used for UI work in the browser. UI development is a typical single-threaded, event-driven model, so JavaScript also came to treat asynchronous processing as its main programming paradigm.

With the success of JavaScript, more and more people began to apply it to other scenarios. At the same time, people increasingly found that asynchronous processing is not the most appropriate choice in many of those scenarios.

Back to Basics, Agile Development

At the framework level, fibjs uses fibers to isolate the business complexity introduced by asynchronous calls and wraps asynchronous I/O handling in more intuitive synchronous calls. Engineers only need to write code following ordinary synchronous business logic to enjoy the great convenience that asynchronous processing brings.

The following code is taken from the documentation for the mysql module:

conn.beginTransaction(err => {
                            if (err) {
                                throw err;
                            }
                            conn.query('INSERT INTO posts SET title=?', title,
                                (error, results, fields) => {
                                    if (error) {
                                        return conn.rollback(() => {
                                            throw error;
                                        });
                                    }

                                    var log = 'Post ' + results.insertId + ' added';

                                    conn.query('INSERT INTO log SET data=?', log,
                                        (error, results, fields) => {
                                            if (error) {
                                                return conn.rollback(() => {
                                                    throw error;
                                                });
                                            }
                                            conn.commit((err) => {
                                                if (err) {
                                                    return conn.rollback(() => {
                                                        throw err;
                                                    });
                                                }
                                                console.log('success!');
                                            });
                                        });
                                });
                        });

In fibjs, the code for the same task looks like this:

conn.trans(() => {
                            var result = conn.execute('INSERT INTO posts SET title=?', title);
                            var log = 'Post ' + results.insertId + ' added';
                            conn.execute('INSERT INTO log SET data=?', log);
                        });
                        console.log('success!');

If you are after conciseness, you can even write the code like this:

conn.trans(() => conn.execute('INSERT INTO log SET data=?',
                                'Post ' + conn.execute('INSERT INTO posts SET title=?', title).insertId +
                                ' added'));
                        console.log('success!');

We can clearly see the difference between the two programming styles. Less code means fewer errors, and as the code shrinks its logic also becomes clearer, which benefits both development and maintenance.

Embrace High Performance

Although we can easily improve response speed by adding more servers, performance should still be one of the key criteria when choosing a development framework. With the release of ES7, async was introduced into JavaScript as a new asynchronous development model. Yet while we enjoy the synchronous style that async brings, we also have to face its impact on performance.

We can use a small test to compare the performance of these different programming styles:

var count = 1000;

                        async function test_async(n) {
                            if (n == count)
                                return;
                            await test_async(n + 1);
                        }

                        function test_callback(n, cb) {
                            if (n == count)
                                return cb();

                            test_callback(n + 1, () => {
                                cb();
                            });
                        }

                        function test_sync(n) {
                            if (n == count)
                                return;
                            test_sync(n + 1);
                        }

                        async function test() {
                            console.time("async");
                            await test_async(0);
                            console.timeEnd("async");

                            console.time("callback");
                            test_callback(0, () => {
                                console.timeEnd("callback");
                            });

                            console.time("sync");
                            await test_sync(0);
                            console.timeEnd("sync");
                        }

                        test();

On the latest V8 engine, this code produces the following results:

async: 14.283ms
                        callback: 1.03ms
                        sync: 0.106ms

The test results make it clear that once async is widely used in a project, the server spends a great deal of time handling calls to and returns from async functions. We have also seen this in real-world tests of server-side applications. Such a sharp drop in performance is completely unacceptable.

Because it uses fibers, fibjs can take full advantage of the JavaScript language itself and get the most out of V8's superior performance. Engineers can easily push server performance to the limit.

Choose Paradigms Flexibly Without Being Held Hostage

Choosing to use fibjs does not mean you have to adopt a synchronous development style. In fact, fibjs supports every asynchronous programming paradigm you have ever seen, and you can switch flexibly between synchronous and asynchronous styles.

Both callbacks and async share one fatal flaw: they are contagious. As long as one function is a callback or async, every other function that depends on it must also be a callback or async. In large-scale software development, this creates enormous development costs.

Take a simple server development scenario as an example. Early in the project, we chose in-memory storage for session data, so we could read and store data directly in the sync style and build the complete business logic on top of it. As the business grows, we need to store session data in redis or mongodb, and then we have to change the session-related operations to async mode.

In theory, we could modify each function one by one so that it meets the requirements of the functions it depends on, but that would require us to fully understand every module and be able to change it. That is completely impossible when several people develop together or when third-party modules are used.

Therefore, every general-purpose module needs to provide both sync and async interfaces to strike a balance between asynchronous processing and performance. Most ordinary developers, however, choose to provide only async interfaces, which leads to a performance disaster.

In fibjs, you can easily solve problems like this and avoid the uncontrolled spread of explicit asynchrony:

var util = require('util');

                        function session_get(sid) {
                            return sdata;
                        }

                        async function async_session_get(sid) {
                            return sdata;
                        }

                        function callback_session_get(sid, cb) {
                            cb(null, sdata);
                        }

                        data = session_get(sid);
                        data = util.sync(async_session_get)(sid);
                        data = util.sync(callback_session_get)(sid);

fibjs can use util.sync to turn callback or async functions into sync functions and call them directly. In this way, we can easily integrate modules written in different programming paradigms and convert them to the sync paradigm at minimal development cost, effectively avoiding the disaster caused by paradigm contagion.
